# Подключение сервисов

## Где находятся настройки

В Django Admin → «Настройки и страницы» → «Настройки магазина» находится переключатель локального режима. Раздел «Интеграции и уведомления» → «СДЭК, ЮKassa, почта и Telegram» содержит сгруппированные поля и сводку готовности. Сохранение настроек не отправляет уведомлений.

Ключи вводятся отдельными полями пароля. Пустое поле сохраняет прежний ключ; отдельный список позволяет удалить ключ. Секреты шифруются Fernet; ключ шифрования и секрет Django находятся в `backend/.local/keys.json`, вне Git. В Windows на `.local` отключено наследование ACL, доступ предоставлен текущему пользователю и SYSTEM.

## Локальная проверка

При включённом локальном режиме можно выбрать города и ПВЗ, рассчитать ПВЗ/курьера, оформить заказ и подтвердить оплату без списания. Локальные адреса и тарифы не являются актуальным справочником СДЭК. Письма и Telegram фиксируются как «Имитировано». Ни SMTP, ни Telegram, ни платёжный API в этом режиме не вызываются.

События оформления и оплаты создают по три уведомления: покупателю, магазину, администратору Telegram. HTML можно посмотреть из списка уведомлений. Кнопка повторной отправки обрабатывает только ошибки и очередь. В реальном режиме она совершает настоящую отправку.

## СДЭК

1. Укажите Account и секрет, город отправления, тариф до ПВЗ и курьерский тариф.
2. Для проверки с реквизитами СДЭК оставьте флаг тестового API; для рабочего договора переключите его на реальный API.
3. Включите СДЭК и отключите локальный режим магазина только после заполнения необходимых подключений.

Адаптер использует OAuth, справочник городов, пункты выдачи и калькулятор тарифа. В заказе сохраняются код города, код ПВЗ, адрес, срок, стоимость и параметры упаковки товаров. Выбранный ПВЗ перепроверяется сервером. У каждого товара редактируются вес и габариты.

**Граница:** автоматическое создание накладной и вызов курьера не включены. После оплаты магазин оформляет отправление в СДЭК и записывает трек-номер в заказ; затем доступно действие «Передать в доставку».

Документация: [портал API СДЭК](https://apidoc.cdek.ru/), [интеграции СДЭК](https://www.cdek.ru/ru/integration/).

## ЮKassa

1. Укажите shopId, секретный ключ и HTTPS-адрес витрины. Для проверки используйте реквизиты тестового магазина ЮKassa.
2. Включите ЮKassa. Перед реальными продажами настройте фискализацию по договору и корректные коды налогообложения/НДС. Передача чеков включается отдельно.
3. Зарегистрируйте HTTPS webhook `/api/webhooks/yookassa/` на события `payment.succeeded` и `payment.canceled`.

Сумма и товары определяются сервером. Для каждой покупки хранится постоянный Idempotence-Key. Webhook не доверяет присланному статусу: платёж повторно запрашивается по API ЮKassa, проверяются сумма, валюта и заказ. Страница заказа также сверяет статус с провайдером. Повторное подтверждение не списывает остатки второй раз.

Если внешний платёж уже создан, его резерв не снимается только по локальному таймеру: платёж мог пройти с задержкой webhook. Используйте действие «Проверить оплату в ЮKassa» в заказах. Отмена у провайдера освобождает резерв. Без внешнего платежа и в локальном режиме просроченный резерв освобождается при обращении к каталогу/оформлению. Постоянный фоновый процесс для локального запуска не требуется.

**Граница:** автоматические возвраты денег, частичные возвраты и автоматическая сверка по расписанию не входят в текущую основу интеграции.

Документация: [формат API и идемпотентность](https://yookassa.ru/developers/using-api/interaction-format), [входящие уведомления](https://yookassa.ru/developers/using-api/webhooks).

## Email и Telegram

SMTP: сервер, порт, STARTTLS/SSL, логин, пароль, адрес отправителя и email магазина. Telegram: токен бота и ID чата администратора. HTML-письма находятся в `backend/templates/emails/`; у каждого письма есть текстовая версия. Пример оформления — `docs/previews/order-email.html`.

Не удалось отправить — уведомление сохраняется с ошибкой и доступно для повторной обработки из админки. Создание заказа не отменяется из-за ошибки SMTP/Telegram.

## Перед production

В текущей среде проверены локальные адаптеры; внешние операции требуют реквизитов и отдельной проверки с провайдерами. Не переносите локальные тестовые заказы в рабочую базу.

Установите `DJANGO_DEBUG=0`, `LOCAL_DEVELOPMENT=0`, независимые `DJANGO_SECRET_KEY` и `ENCRYPTION_KEY`, `DJANGO_ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`; используйте HTTPS. Ключ шифрования должен соответствовать зашифрованным настройкам импортируемой базы. В production локальный режим блокируется. `.env` автоматически не читается: переменные задаются окружением сервера.

Раздавайте `frontend/dist`, `/api` и `/admin` направляйте в Django, `/media` — в каталог медиа, `/static` — в собранную статику Django. Для предрендеренных публичных маршрутов отдавайте соответствующий `index.html`; неизвестным маршрутам — `404.html` со статусом 404, служебным `/checkout`, `/order/*`, `/payment/*` — оболочку приложения. Секретные ссылки заказов не должны попадать в стороннюю аналитику или публичные access-логи.

Заполните реальные контакты, реквизиты, утверждённые условия покупки/возврата/обработки данных и заново соберите публичные страницы. Изменение контента сразу видно через API; поисковый HTML обновляется следующей сборкой.
